Memory: a Hopper case study

How to fit it on 80 GiB.

GPU memory is kind of like oxygen: you don't really think about it until you run out, at which point you care about nothing else. Fortunately, it is comparatively simpler to debug OOMs in LLM pretraining, because the memory usage of your trainer doesn't depend on doing distributed communications at scale (assuming your memory allocations and deallocations are deterministic--a very good idea!) In modern PyTorch, you can use fake ProcessGroup (fake PG) to do a very high fidelity simulation of the memory usage of any given rank in an arbitrarily large training config on a single GPU.

However, it's good to have an expectation about how much memory your model should be using, given choices on parallelism, activation checkpointing and low precision, so you can tell if your implementation is buggy and using more memory than it should be. It's also helpful to know what levers you have available for reducing memory usage: you will often be in a regime where your hero run can just barely fit your model in memory, and you're trying to make it fit without sacrificing too much MFU. For example, the original DeepSeek-V3 pretrain was done on 2048 H800 GPUs (same amount of memory as any H100), as we'll see, memory is pretty tight in this setting!

This post is organized as follows: first, we'll recap at a high level what memory is used for in LLM training. Next, we will individually discuss each knob you have for adjusting memory usage, using simplified models to build intuition for how these knobs affect memory. Then we'll put it all together to reproduce DeepSeek-V3's 2048 GPU Hopper training configuration. Credit where credit is due: this analysis is based off of an unpublished analysis done by Daniel Haziza.

What is memory used for in training?

While your exact memory usage depends on implementation details of your training framework, it's still possible to reason through what the major consumers of memory will be: at a high level, you need to spend memory on parameters, optimizer states, activations (saved for backwards) and gradients. Now, exactly how much memory you will need on a single GPU depends on both parallelization choices (how we are distributing things across ranks) as well as our direct memory adjustment knobs (activation checkpointing, low precision). But to keep things simple, let's first work out the global (across all ranks) memory usage of DeepSeek-V3 training assuming everything in bfloat16 and no activation checkpointing.

Activation checkpointing

At the end of the forward pass you are at (or near) the memory high-water mark, because autograd is keeping alive every intermediate activation that the backward pass will need. Activation checkpointing (also called rematerialization) is the observation that you don't have to save a tensor for it to be available in backward: you can recompute it on the spot from something earlier that you did save. You pay FLOPs, you get back bytes.

Here is the transformer block diagram from the last post, now with a save/recompute control on every operation. Each op is marked either 💾 (save its output for backward) or ↻ (recompute it during backward). The annotations on the wires are derived from those marks: the diagram works out which tensors backward actually reads, and therefore which ones must stay resident. For now, assume every saved tensor is stored in bf16 (2 bytes per element) — that's what the byte counts and the yellow memory grids are priced at; we'll revisit that assumption in the next section.

Some things to notice as you play with the marks:

  • Marks go on operations, not tensors. If you mark an op ↻, its output no longer needs to be saved — but the inputs it reads now do, because the replay has to start from something. The diagram computes this transitive closure for you. (A diagram that let you mark tensors directly would let you express incoherent policies.)
  • The block is the checkpoint region. Its input x0 is always saved (the 🔒): it is the anchor that every chain of recomputation eventually terminates at. The block's output is the next block's x0, so it is charged there.
  • The DeepSeek-V3 paper states its policy outright: recompute the RMSNorms, the MLA up-projections, and SwiGLU. That's the dsv3 preset the diagram starts in. Notice what these ops have in common: they are cheap to rerun (elementwise, or small GEMMs) and their outputs are large. That's the whole game — spend FLOPs where they are cheap, save bytes where they are big. The tally in the caption prices the replay.
  • Production policies go much further. Try marking every op in the MLA column ↻ (norms, projections, attention, even the residual add). Backward then replays the entire attention half from x0 — about +40% of forward FLOPs — and in exchange the attention side of the block stashes exactly one tensor. We'll use this policy in the case study below.

Low precision

The second lever is to store the bytes you do keep in a smaller format. On Hopper, DeepSeek's recipe runs the big GEMMs in FP8 (E4M3) with fine-grained scaling: one fp32 scale per 1×128 tile of elements, which works out to a ~3% overhead on top of 1 byte per element. Our model adopts a simplifying convention that is worth making explicit: a saved activation is stored in the dtype of the GEMM that will read it during backward. Flip the dtype buttons below and watch the stash sizes follow.

Two recipes matter for us. The dsv3-fp8 recipe is the Hopper one: linears in tile-scaled FP8, but the attention core, its output, and the router kept wide — not everything survives quantization. The nv-mxfp8 recipe is the Blackwell one (we'll meet it again in the MLPerf post): MXFP8 with power-of-two block scales on every GEMM, including FP8 attention. One Hopper-specific tax deserves a callout: the weight gradient GEMM reads its activations transposed, and 1×128 per-row scales don't survive a transpose — so on Hopper, FP8 stashes that feed a wgrad are kept in both orientations. Turn on the fp8ᵀ toggle above and watch the ᵀ×2 tags appear. MXFP8's power-of-two scales requantize exactly across a transpose, so Blackwell keeps one copy. (The kernel-level story of how these GEMMs actually run can wait; it doesn't matter for memory.)

Parallelism

Neither lever above touches the other half of the memory bill: weights, gradients, and optimizer state. For a 671B-parameter model this is the elephant — at bf16 weights, fp32 gradient accumulators, and an fp32 + 2×bf16 Adam, you are staring at multiple terabytes before the first token flows. This is what parallelism divides:

  • FSDP / ZeRO shards states across the data-parallel ranks. ZeRO-1 shards just the optimizer; ZeRO-3 shards weights and gradients too, at the cost of all-gathering layers on demand.
  • Expert parallelism shards the experts — and in a model where the routed experts are ~95% of the parameters, EP is doing most of the work. At EP64, each rank holds 256/64 = 4 experts per layer.
  • Pipeline parallelism divides the layers across ranks. But note the catch: at 1F1B steady state, stage s holds min(pp−s, m) microbatches of activations in flight, so the first rank keeps roughly pp microbatches alive. Fewer layers per rank × more microbatches in flight ≈ a wash for activations; PP divides weights, not stashes.

The interplay between all three (plus the two levers) is why the final calculation is worth actually doing, so let's do it.

Fitting DeepSeek-V3 on Hopper

Configuration. We work a 288-routed-expert DSv3-family variant (62 MoE layers — modeled all-sparse, a simplification; the real family stacks 3 dense blocks first, see the structure widget below — vocab 128000, no MTP) trained on 2048 H100-class GPUs: FSDP-replicas 4 × PP 8 × EP 64 (our decomposition: gpus=2048, pp=8, ep=64 → dp=256, dp/ep=4), seq 4096, mbs 1, 64 microbatches. Precision: FP8 GEMMs with 1×128 tile scales (weights kept ×2 for the transposed copy, +4/128 fp32 scale bytes), fp32 gradient accumulators, a 3-state AMSGrad optimizer sharded over all 2048 GPUs. Recompute: the attn-replay policy from above — replay all of attention from the block input, save the post-norm output plus the fp8 expert inputs and gate/up, recompute swiglu-out. Pipeline in-flight: a DualPipe-style two-chunk layout holds 17 microbatches × 4 layers per chunk ≡ 8.5 microbatches/rank.

Our per-rank inventory

Why this fits on 80 GiB. Three modeling points carry the number. (1) Gating placement: the router's gate weights are applied to the swiglu output before the linear down-proj — mathematically identical to gating the expert outputs, and it makes the expert outputs a pure intermediate rather than a ~30 GiB stash for the combine's backward. (2) The attn-replay policy: because all of attention replays from the block input, the mid-layer residual (x1), the MLA latents, the softmax lse, and the SDPA output are never stashed — the attention side of the block saves exactly one tensor, the post-norm output that the MoE half consumes. The cost is ~+40% of forward FLOPs replayed in backward: the Hopper-era activation-checkpointing pressure in one number. (3) The in-flight law: DualPipe's two-chunk schedule halves the naive (2·PP+1) in-flight count per layer, so the activation column is 8.5×, not 17×.
