Can DeepSeek-V3 just be sharded? The FSDP sweep

DRAFT (unlisted study). Prose below is AI-drafted and awaits a human edit pass — see the disclosure footnote.1

Suppose you have a cluster of H800s and a copy of DeepSeek-V3, and you have not yet decided how to lay the model across the GPUs. The first fact is that you must decide something: 671B parameters of bf16 weights alone are 1.25 TiB, and one GPU has 80 GiB. There are only two ways to spread them. Either the parameters are sharded and gathered — every GPU stores a slice, and the slices are reassembled over the network whenever they are needed, which is what ZeRO and FSDP do — or the work is partitioned, so that a GPU only ever touches the parameters it owns and sends activations instead. This study prices the first route at speed of light, before any other parallelism is on the table.

Five inputs

The whole calculation runs on five numbers, none of which requires a memory model of the training step.2

From these: one step of speed-of-light compute is 30,720 × 250.5 GFLOP at 1,979 TFLOP/s, or 3.9 seconds. Every step also has to move gradients and weights, and that cost depends on G, the number of GPUs a parameter is sharded across. The chart sweeps G from 1 (every GPU holds the whole model) to the full cluster (every GPU holds one 2,048th).

Each row is one sharding degree. On the left, the bytes each GPU holds at rest, in the byte-component colors of the memory posts; the shaded region is past the 80 GiB the GPU has. On the right, the time the step's collectives take at raw link bandwidth: the gradient reduction, a reduce-scatter over the G-way shard group followed by an all-reduce of each shard across its replicas, and the one all-gather that brings the updated weights back.3 The solid line is the speed-of-light compute the sync would have to hide behind; the dashed line is DeepSeek's realized step at their reported 1,475 tokens per second per GPU. Both scale with tokens per GPU, so the cluster and batch knobs move them together. Hover a row for the exact terms.

Reading the sweep

  • ZeRO-1 and ZeRO-2 never fit. They shard the optimizer state, and ZeRO-2 the gradients too, but leave the bf16 weights replicated, and those alone are 1.25 TiB on every GPU. Flip the first knob: the memory bars barely move as G grows, because the part being sharded was never the problem. Only ZeRO-3, which shards the weights as well, has a memory curve that reaches 80 GiB at all — and it needs G of at least 110 for the parameter state alone, before a single activation is stored.
  • The sync cost is almost flat in G. A ring collective moves (G − 1)/G of the bytes through every GPU, so G = 2 already pays half the full cost and G = 8 pays 88% of it. The one real step in the right-hand panel is the node boundary: below it the shard group sits on NVLink at 200 GB/s, above it every GPU is talking through its 50 GB/s NIC, and the time jumps fourfold. There is no sweet spot to tune toward. Sharding a little buys almost no memory and still costs most of the traffic.
  • The pincer. Memory forces G ≥ 110, which is fourteen nodes and therefore InfiniBand. Bandwidth past a node costs about 80 seconds of sync per step against 3.9 seconds of speed-of-light compute, and against the 21-second step DeepSeek actually achieved. Inside a node the sync would be a tolerable few times compute, but memory is over by more than an order of magnitude. No G satisfies both. This is the precise form of "FSDP is communication-bound or out of memory": it is not one or the other, it is one and then the other, with no gap between them.

Sparsity is the culprit

Now flip the model knob to the dense counterfactual: a model with DeepSeek's active parameter count, 36.6B, which does the same FLOPs per token and therefore has the same compute line. Its ZeRO-3 memory curve crosses 80 GiB at G = 8, exactly one node, and there the sync runs on NVLink and comes in under two seconds, below speed-of-light compute with room to spare. FSDP is a perfectly good answer for a dense model of this size. What breaks it for DeepSeek-V3 is that parameter traffic scales with the total parameters while compute scales with the active ones, and for this model those differ by a factor of eighteen. The same ratio is why a mixture-of-experts model is cheap to run; here it is what makes it expensive to synchronize.

The cluster knob makes the same point from the other side. Tokens per GPU per step is the batch divided by the world size, so at a fixed batch the sync-to-compute ratio grows linearly with the number of GPUs. Speed of light breaks even at roughly 320,000 tokens per GPU per step, which at DeepSeek's batch is about 200 GPUs, and on 200 GPUs the memory column says no anyway.

What this decides, and what it doesn't

The gradient column in the chart is not specific to FSDP. Any data parallelism pays a synchronization cost proportional to the parameter bytes each GPU is responsible for. ZeRO keeps that responsibility at the whole model and only spreads the storage; the traffic follows the responsibility, not the storage. Partitioning the work — by pipeline stage, by expert, by tensor slice — shrinks the responsibility itself, and the memory column and the sync column collapse together. On 2,048 GPUs a full partition leaves each GPU answering for about 330M parameters. So "FSDP versus model parallelism" is less a choice between two strategies than one slider, how many parameters does each GPU answer for, and DeepSeek-V3's sparsity pushes it hard toward the partitioned end.

What the sweep does not tell you is which partition. Once the parameters are partitioned, the question becomes which arrangement of pipeline, expert, and data parallelism fits in 80 GiB with the activations included, and that is a memory question — the one the Hopper memory post takes up. It also does not tell you that partitioning is free: sending activations instead of parameters has its own per-token bill, and whether it hides behind compute is the subject of the timing posts.
