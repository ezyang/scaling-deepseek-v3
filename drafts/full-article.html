What should a DeepSeek-V3 training profile look like?

When doing performance optimization, it is important to have a good picture of what your system performance is supposed to be. Does it matter if you managed to 10x the speed of your program? Not if it was already running 100x slower than it was supposed to be. In LLM training, the first method by which we gain this picture is a roofline analysis, which abstracts away implementation details of the training framework and computes what the speed would be if everything was (typically unachievably) optimal.

A roofline can be a starting point for a more refined model of how performant your training system is supposed to be.

When you open a Perfetto trace of a big training job, you are looking at the sum of a dozen effects — kernel efficiency, pipeline bubbles, exposed communication, launch overhead, stragglers — collapsed into one picture. This essay inverts that: we simulate the profile of a DeepSeek-V3 pretraining step from first principles, adding one correction term at a time, ordered by impact on the headline number. Each refinement doubles as an elimination round: as the model learns about a new cost, whole regions of the parallelism configuration space get ruled out, until only the defensible configs survive. We work on a cluster of 256 GB300 NVL72 GPUs (288 GiB HBM, 72-GPU NVLink domains), sequence length 4096 — 256 because that is the scale we have the most real traces to check against. Cluster size is a knob (gpus, with dp = gpus/pp) in every widget and the sandbox.

Workshop state: the memory step below is the first section in this style; the timing refinements (bubbles, all-to-all, DP comm, …) will follow one by one. The simulator itself already models them — see the sandbox at the end of the memory section, where every effect toggles independently. Traces render in a small Perfetto-style viewer with Perfetto navigation (W/S zoom, A/D pan, drag, F focus, M mark, 0 fit) and export to the real ui.perfetto.dev. All hardware numbers are editable assumptions in src/model.js.

Step 0 — does it even fit?

Before any timing question, a configuration must pass a boolean gate: does one training step fit in HBM? Fitting is a statement about the high watermark, not about everything you ever allocate — and forward-pass temporaries are deliberately ignored here; kernel workspace is not set in stone. The watermark decomposes per GPU into weights (BF16 working copy + a resident low-precision copy where the recipe uses one), gradients (BF16), optimizer state (FP32 master + BF16 Adam moments ≈ 8 B/param, DeepSeek-style), activations stashed for backward — split into MLA stashes, MoE stashes, the residual stream, and logits — and working buffers (a2a send/recv, FSDP’s gathered layer, an unsharded gradient bucket). Because pipeline parallelism changes the activation law so drastically, we run the analysis twice: first without PP, then with it.

Precision choices thread through everything, so we fix them first. Whatever backward will read is stashed at the precision of the matmul that reads it, so the recipe is a per-matmul decision. For the essay we default to the Blackwell-native MXFP8 recipe from NVIDIA’s NeMo/Megatron-Bridge DSv3 runs — every GEMM in MXFP8 (32-element blocks, UE8M0 scales); attention core, router and head in high precision. NVIDIA’s published result with this recipe is our calibration anchor: 256 × GB300, TP1 · PP2(×8 virtual) · EP32, mbs 1, batch 4096 sequences → 6,338 tok/s/GPU (10.3 s/step) — the number the simulated profile must eventually explain. The original DeepSeek-V3 FP8 recipe is a preset too — its tile-wise fp32 scales (4 B per 128 elements) cost exactly the same 1/32 byte-per-element overhead as MX block scales, so one constant models both. The transformer-block schematic in the sandbox at the end of this section is the model’s single source of truth for precision — its per-matmul choices drive the memory widgets and the simulated profile (and, later, the rooflines).

And parallelism is an input to the memory calculation — pipeline parallelism in particular is allowed to make things fit — so we put the knobs on the table before any bars. The controls below set the shared baseline (hardware, cluster size, microbatch, sequence length) for every memory bar in this section. You specify the parallelism — pp × dp, with EP a sub-grouping of dp — and the global batch; everything else is derived in the open: gpus = pp × dp, one 4096-token sequence per microbatch (mbs = 1), microbatches per step m = GBS ÷ dp, and — assuming a 1F1B schedule — stage s holds min(pp − s, m) microbatches of stashes in flight. The variants directly below inherit everything — including pp — pinning only the one thing that defines them, so sweep the pp knob to see which schemes fit at which pipeline depth. (The Analysis A/B rows further down pin their own parallelism; that's their point.)

Analysis A — no pipeline

With pp = 1 the activation law is trivial: exactly one microbatch of full-model stashes is live at a time (backward frees layer by layer as it goes). The question is parameter state: 671B params × ~12 bytes of state must land on 256 GPUs somehow. Candidates, worst-stage watermark against each row’s own capacity line:

  • Replication is dead on arrival (7.5 TiB, 27× over) and ZeRO-1 alone barely helps (3.1 TiB): replicated weights + gradients are the wall. Something must shard the weights.
  • EP is weight sharding. ZeRO-1 + EP64 fits (~186 GiB) with no FSDP machinery at all — sharding the experts 64 ways removes 97% of the parameter problem. FSDP without EP also fits (~134 GiB) but pays a 65 GiB working set gathering whole MoE layers; FSDP + EP64 is comfortable (~75 GiB).
  • Recompute is optional on GB300 without PP: stash-everything is ~107 GiB, since only one microbatch is ever live; mbs = 4 with selective recompute is ~171 GiB. Context length is the non-PP wall: seq 32k lands at ~298 GiB — just over the line.
  • The hardware rows are closer than they used to be. The 75 GiB config fits an 80 GiB H800 too — barely, and only with selective recompute (stash-everything is 107 GiB, dead on Hopper). At 256 GPUs, parameter state alone is ~32 GiB with FSDP+EP (~21 GiB of it optimizer), so an H800 lives within ~5 GiB of its life; on GB300 the same config leaves 200+ GiB of headroom — room for bigger microbatches, longer context, or skipping recompute entirely. That headroom is the finding, and it is why the timing sections, not memory, will pick the GB300 config.

Analysis B — with pipeline

PP changes both sides of the ledger. It divides parameter state by pp. But under 1F1B, stage s must hold min(pp−s, m) microbatches of forward stashes, so the early stages hold up to pp× more activations — while owning pp× fewer layers. The product is nearly invariant: layers/pp × pp ≈ layers. PP redistributes activations; it only truly shrinks parameters.

  • On GB300 at mbs = 1 the watermark is a wash with the best non-PP config (~74 GiB either way): the parameter savings and the in-flight activation multiplier cancel almost exactly.
  • No-recompute still fits (~106 GiB); mbs = 4 without recompute does not (~289 GiB) — with PP the activation side reacts 15× faster to every microbatch/sequence-length decision.
  • On 256 H800s, PP16 + selective recompute fits at ~74/80 GiB — the same near-the-edge story as non-PP, with no extra margin bought by the pipeline: PP’s parameter savings went to the in-flight activations. Skipping recompute (106 GiB) is GB300-only either way.

Survivors so far, on 256 × GB300: memory eliminates replication and bare ZeRO-1 — and almost nothing else. Non-PP (FSDP or ZeRO-1, with EP) and every reasonable PP · EP with selective recompute all fit with 200+ GiB of headroom; even an H800 squeaks by at ~74/80 GiB once recompute is on. Memory is not the discriminator at this scale; what it buys GB300 is slack — bigger microbatches, longer context, no recompute — and the timing sections will decide what that slack is worth.

Sandbox — one config: block, memory, profile

Everything here is linked. The transformer-block schematic sets each matmul’s precision and each op’s save 💾 / recompute ↻ mark; the controls set hardware, parallelism and schedule; every simulated effect toggles independently. All of it drives both outputs at once: the memory watermark and the simulated profile for the same configuration. Start from the non-PP survivor and walk it toward PP16, push seqLen/mbs until the bar goes red, try globalBatch: 30720 (m = 120 at dp 256, the real run's depth), H800 with only expert a2a on, granularity: op zoomed into a single MoE layer, or dpRanksToSim: 4 with jitter on.

Every trace widget carries the memory verdict in its caption; anything red cannot exist. Recompute marks now charge time too: each op marked ↻ replays its forward during backward (the "recompute (fwd replay)" slices in the trace; under full checkpointing the a2a replays as well). Precision currently drives memory (and soon rooflines); the trace’s kernel timings still use the coarse dtype knob.

Checking the estimate against reality

A simulator you can't falsify is a toy. Every widget's ⤓ trace.json button and scripts/export.mjs emit standard Chrome trace JSON, and scripts/compare.mjs summarizes any PyTorch-profiler/Kineto trace into the same per-category, per-GPU busy-time budget (GEMM / attention / all-to-all / FSDP collectives / p2p / vector) and prints sim-vs-real ratios:

node scripts/compare.mjs real_rank0_trace.json \
    --config '{"hardware":"h800","dtype":"mxfp8","microbatches":120}'

Step boundaries come from ProfilerStep# annotations when present. Ratios near 1.0 mean the model explains that category; a big miss tells you which refinement to improve — or which assumption (GEMM efficiency, NIC bandwidth, overlap) your cluster violates.

What this doesn't model (yet)

  • DualPipe / a2a–compute overlap — the fix for the exposed all-to-all, and the most interesting upcoming refinement.
  • Output-form RMSNorm backward (running off the norm's output + rstd — the trick that gets the residual stash down to one copy per layer), MTP module, optimizer EMA copies.
  • Critical-path stitching across all ranks (we show representative ranks; with stragglers the interesting view is "the ranks that must speed up for the step to speed up").
  • Interleaved/virtual pipeline stages, network congestion.
